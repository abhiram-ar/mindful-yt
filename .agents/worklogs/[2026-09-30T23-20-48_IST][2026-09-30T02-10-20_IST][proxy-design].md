# Why yt-dlp goes through a local proxy

The hosts file only affects the system resolver, so any program that does its
own lookups gets past it. The first version was Python: it ran yt-dlp as a
library and patched `socket.getaddrinfo` in-process, with no proxy needed.

The Go version runs `yt-dlp` as a separate program, so an override inside ytget
can't reach it. yt-dlp has no option to map hostnames to addresses. It does
have `--proxy`, and with an HTTP proxy it never resolves the target itself: it
sends `CONNECT www.youtube.com:443` and the proxy does the lookup. So ytget runs
a small CONNECT proxy and resolves YouTube there.

## Rejected alternatives

- Editing the hosts file or system DNS: lifts the block for everything.
- Passing IP addresses to yt-dlp: TLS certificates are tied to names, and
  yt-dlp only accepts youtube.com links.
- yt-dlp as a Python library: brings Python back.

## What keeps it safe

- Bound to `127.0.0.1`, on a random port, only while ytget is open.
- CONNECT only: it relays TLS and never sees plaintext.
- A new random password each run (`Proxy-Authorization`), so other local
  programs can't use it.
- DNS-over-HTTPS (Cloudflare `1.1.1.1`, then Google `8.8.8.8`) only for
  `youtube.com`, `youtu.be` and their subdomains. Video data comes from
  `*.googlevideo.com`, which isn't blocked and uses the normal lookup.

The release yt-dlp bundles `curl_cffi`, which does its own DNS. That would have
defeated an in-process override, but a proxy covers every HTTP library.
