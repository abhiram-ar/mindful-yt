# lock-me-in

`mindful-yt lock-me-in` blocks YouTube in the OS's hosts file, for users who
haven't blocked it by hand. It asks two Yes/No questions, both starting on No,
then counts down 10 s ("Locking you in, bud...", esc cancels), then writes.
mindful-yt keeps working afterwards: the proxy resolves YouTube over DoH and
never reads the hosts file. There's deliberately no unlock command.

## What it writes

Five domains (`youtube.com`, `www.youtube.com`, `m.youtube.com`, `youtu.be`,
`www.youtu.be`), each as `0.0.0.0 <domain>` and `:: <domain>`, under a
`# Blocked by mindful-yt lock-me-in on <date>` comment. The user picked the
list, including the IPv6 lines and `www.youtu.be`.

- IPv6 lines: with only IPv4 entries, a browser or OS (macOS especially) can
  still look up YouTube's IPv6 address and get through.
- A domain counts as blocked when an entry maps it to any loopback or
  unspecified address (`127.x`, `0.0.0.0`, `::1`, `::`), per address family.
  So a file blocked by hand with `127.0.0.1` only gets the `::` lines added.
- An entry pointing a domain at a real address is a conflict
  (`hosts.ConflictError`). Appending can't override it, so mindful-yt
  stops and names the line to remove.
- `hosts.Append` only appends: ACLs, owner and attributes stay as they were.
  Line endings match the file, and a second run adds nothing.

## How it fits together

- `internal/hosts`: `Lines`, `Check`, `Append`, `Path` and `FlushDNS`, with
  OS-specific files.
  - On Windows, `Path` comes from the registry's `DataBasePath`.
  - `FlushDNS` runs `ipconfig /flushdns`, or `dscacheutil` plus
    `killall -HUP mDNSResponder` on macOS, or `resolvectl` on Linux.
  - `FlushDNS` is separate from `Append` so tests never flush the machine's cache.
- `cmd/mindful-yt/lock.go`: `run()` sends `lock-me-in` here **before
  `store.Dirs()`**. Elevated, it may run as another user (UAC with an admin
  account) or as root (sudo), and `store.Dirs` could create or move that
  account's folders.
  - The "already blocked" notice comes before the terminal check.
  - The hidden `lock-me-in --write-hosts` is what runs as admin.
- `internal/platform`: `IsAdmin`, `AdminCommand` and `ErrDeclined`.
  - **Unix:** sudo, or doas, with the absolute path from `os.Executable()`.
    `sudo mindful-yt` would fail, because `~/.local/bin` isn't on sudo's
    `secure_path`.
  - **Windows:** `ShellExecuteExW` with the `runas` verb, `SW_HIDE`, then a wait
    on the process. x/sys has no `ShellExecuteEx`, so it's loaded from
    shell32. A test checks the struct size (112 bytes on 64-bit, 60 on 32-bit).
    `ERROR_CANCELLED` means the user declined UAC.
- `internal/tui/lock.go`: `lockModel`, run by `tea.Exec`, so sudo gets the
  terminal for its password.
  - After writing, it reads the file back: the lines being there is what
    counts, not the helper's exit code.
  - It's built from Bubbles: `timer` for the countdown, `key` and `help` for
    the help line.
  - The countdown is just the line "Locking you in, bud... 8s". The user tried
    a draining bar (Bubbles' `progress`, then a yellow-to-red gradient) and
    dropped it.
- `internal/tui/keys.go`: the user asked for Bubbles components wherever
  Bubbles has one. So every screen now uses `key.Binding`s, with
  `help.ShortHelpView` for the help line.
  - Bubbles has no Yes/No component, so the prompts use the app's own `›` rows.
    The user turned down `huh`.
  - `help` keeps an item whose "…" wouldn't fit either, so `helpLine`
    truncates as a backstop.

## Tested

- Unit tests on Windows. For Linux, see below.
- WSL resolves youtube.com through Windows's hosts file (it gave 127.0.0.1),
  so locking in on Windows covers WSL too.
- **The real Windows flow, run by the user on 2026-10-01.** It went through
  the UAC prompt, the countdown and the write.
  - It added only the 5 `::` lines under the comment, kept the `127.0.0.1`
    lines, and kept every line CRLF.
  - youtube.com then resolved to `127.0.0.1` and `::`.
  - A second run said "already blocked", and downloads still worked.

## Linux

Tested only in WSL (Ubuntu 24.04). The how-to is in the cross-platform
worklog under "Testing Linux here".

**Tested:**
- The `hosts`, `platform` and `tui` test binaries.
- As root, in a mount namespace on a copy of `/etc/hosts`:
  - `lock-me-in --write-hosts` appended the block, and a second run added
    nothing
  - `lock-me-in` said "already blocked"
  - with no terminal, `lock-me-in` refused with exit 2 (it was run before
    the write)

**Not tested:**
- **The interactive screens in a real Linux terminal.** The two questions,
  the countdown and esc are covered only by the `Update`/`View` unit tests,
  which don't depend on the OS.
  - To test them without a person: run as root in the mount namespace
    under `script` (which fakes a terminal), with the keys piped in. As root
    it writes in-process, so there's no sudo step.
- **The sudo step.** As a normal user, after the countdown `tea.Exec` runs
  `sudo <absolute exe> lock-me-in --write-hosts`, and sudo asks for the
  password in the terminal.
  - Only the command building is unit-tested: sudo, else doas, else an error.
  - A real prompt needs the user's password, so the user has to run it.
  - The user can try it in WSL: WSL rebuilds its `/etc/hosts` at every
    start, so `wsl --shutdown` undoes the write.
- **`FlushDNS`** (`resolvectl flush-caches`) ran, but its result is ignored,
  so whether it worked is unknown. WSL may not run systemd-resolved.
- **Real Linux machines outside WSL, other distros, and doas.**
