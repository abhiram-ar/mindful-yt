# Node.js instead of Deno

yt-dlp needs a JS runtime to run YouTube's player code (the n/sig
challenges). mindful-yt used to install Deno for it. It now installs Node.js
and tells yt-dlp to use Node only. This replaces the Deno rows in the
cross-platform worklog.

## Why

- The user heard Deno was being discontinued. What we found: Deno ended its
  **LTS channel** on 2026-04-30 (the last LTS was 2.5), and regular releases
  go on. The user chose to switch anyway, to Node only.
- yt-dlp has a built-in Node provider and runs the same solver script, which
  is bundled in the standalone yt-dlp builds. The minimum is Node 22.0
  (`yt_dlp/utils/_jsruntime.py`).

## How it works

- **`--no-js-runtimes --js-runtimes node`** in `ytdlp.baseArgs`. Deno is
  yt-dlp's only default and ranks above Node, so `--js-runtimes node` alone
  still uses any Deno it finds. `yt-dlp -v` shows
  `JS Challenge Providers: ... deno (unavailable), node`.
- **`deps.InstallNode`:**
  - Finds the newest LTS by streaming `https://nodejs.org/dist/index.json`,
    which lists the newest release first, and stops at the first entry whose
    `lts` isn't `false`. It refuses a version that isn't `vN.N.N`.
  - Checks the download against `<version>/SHASUMS256.txt` with
    `expectedSum`.
  - Unpacks just the program:
    - `node-<v>-win-<arch>.zip`, entry `node-<v>-win-<arch>/node.exe`
    - `node-<v>-<darwin|linux>-<arch>.tar.gz`, entry `.../bin/node`
  - `unzip` and `untarGz` match the exact entry path. The tar side takes
    regular files only, because `bin/npm` and `bin/npx` are symlinks.
  - The Linux download is 58 MB, and node unpacks to 127 MB.
- **`deps.RemoveDeno`** runs at startup, right after `store.Dirs`. It deletes
  the `deno` that older versions put in the tools folder, which yt-dlp no
  longer uses.
- **`Dependency.From`** names where `Download` gets each tool: GitHub for
  yt-dlp, nodejs.org for Node. The install screens used to say "from GitHub"
  for everything, which was true while Deno also came from GitHub.
- **`FindJSRuntime`** looks in the tools folder first, then on PATH. That is
  the order yt-dlp uses, because the tools folder goes first on its PATH.

## Trade-off: the sandbox

- yt-dlp runs Deno with no permissions at all.
- It runs Node with `--permission` (`--experimental-permission` before 23.5).
  That blocks files, child processes and workers. Network is blocked only on
  Node 25+ (`--allow-net`).
- The newest LTS was 24.21.0 on 2026-10-09, so the network isn't sandboxed
  until Node 26 becomes LTS in late October 2026. After that, a new install
  gets 26. An existing tools-folder Node is never updated.

## Open

- **musl (Alpine):** still install by hand, as with Deno. But Node 24.21.0 and
  26.x do publish an official `linux-x64-musl.tar.gz`, and 24.19.0 didn't.
  `InstallNode` could use it on x64 musl. That is untested; there is no arm64
  musl build.
- **Updating Node:** like yt-dlp's Deno before it, an installed Node is never
  updated. `--update` covers yt-dlp only.

## Checked (2026-10-09)

- gofmt, `go vet` for linux, darwin and windows, and `go test ./...` all pass.
- The live tests pass on PATH's Node 26.8.1 while `/usr/bin/deno` is present.
- With a bare PATH (go and ffmpeg only), `InstallNode` installed v24.21.0 and
  left no `.part` files behind. TestLiveProbeAndDownload and
  TestLiveChallengeSolverWorks then passed with `JS runtimes: node-24.21.0`.
- `mindful-yt --history` with a fake `deno` in `MINDFUL_YT_HOME` removes it.
- The container end-to-end check passed all 39 checks. It installed Node
  24.21.0 in a clean Arch system, and yt-dlp used it. That run showed the
  "from GitHub" text on Node's install screen, fixed afterwards. The fix is
  covered by `TestInstallScreensNameEachToolsSource`.
- Not run yet: `install.ps1` pasted on Windows, and macOS.
